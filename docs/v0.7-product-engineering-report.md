# PythonDepot v0.7 Product Engineering Report

## 1. Product understanding

### Confirmed observations

PythonDepot is a FastAPI application for Python package discovery, vulnerability monitoring, package decisions, provenance, portfolio risk triage, Python upgrade planning, trusted reviews, SBOM license policy, analytics, reports, and assisted migration to `uv`. The primary UI consists of a security dashboard and six server-rendered product workspaces.

Likely users are application developers, platform engineers, security engineers, package maintainers, technical leads, and policy administrators. The most repeated workflows are package assessment, reviewing changed risks, acknowledging or resolving findings, checking upgrade blockers, and previewing dependency-tool migrations.

The code already has strong accessibility foundations: skip links, landmarks, labels, keyboard-operable forms, live regions, mobile layouts, explicit empty states, trust caveats, and escaped user content.

### Reasonable inferences

Daily users are likely to return through risk alerts, search repeatedly for the same package across separate screens, preserve filters during triage, and prefer requirements files over hand-authored dependency JSON. Security users need state changes to be durable and auditable. Users may interpret a global “current” freshness label as applying to all evidence even when nothing has been evaluated.

### Optional opportunities

Persistent Projects, repository imports, bulk risk actions, assignment and due dates, source-specific freshness, background jobs, waiver workflow, pull-request creation, and an integrated migration campaign are valuable next steps. They were not implemented in v0.7 to keep the change incremental and testable.

## 2. Improvement summary

### Critical improvements implemented

- Added working risk-inbox filtering by search and state.
- Added inline state transitions that preserve the user’s current filter after submission.
- Added immutable risk transition history with actor, previous state, next state, note, and timestamp.
- Added privacy-conscious telemetry for risk state changes. Dependency contents and risk messages are not included in telemetry.
- Replaced the upgrade planner’s JSON-only behavior with dual support for dependency JSON and requirements-style text.
- Added clear detection and “needs review” feedback for unsupported editable or URL dependency lines.
- Replaced the inaccurate global “Evidence freshness: current” claim with state-aware “Evidence not evaluated” or “Current evidence snapshot” text.
- Added server-side validation for package comparisons, preserving user-entered values and returning an accessible error summary.
- Fixed project packaging so editable installation succeeds and declared `python-multipart`, which is required by FastAPI form routes.

### Secondary improvements implemented

- Added table captions, keyboard-focusable overflow regions, accessible action labels, visible focus styles, reduced-motion support, and better mobile filter layouts.
- Added specific empty-state language for filtered risk results.
- Added count feedback to dependency analysis.
- Updated package version to 0.7.0 and synchronized the root `python_depot_migrate` package with the CLI source.

### Not implemented yet

- Authentication, RBAC, and production multi-tenant authorization.
- Project/repository imports and persistent project workspaces.
- Bulk risk actions, assignees, due dates, and SLA reporting.
- Source-specific evidence timestamps and background job orchestration.
- Complete report persistence and waiver approval workflows.
- Pull-request and ticketing integrations.

## 3. Requirements

### Must-have business and user requirements

- **BR-01:** Frequent risk-triage work must preserve context and require fewer repeated actions.
- **UR-01:** Users must be able to search and filter risk items, change state, and return to the same view.
- **UR-02:** Users must be able to enter normal requirements text in the upgrade planner without building JSON manually.
- **UR-03:** The UI must not claim evidence is current before evidence has been evaluated.
- **UR-04:** Invalid comparison input must preserve the user’s work and explain how to correct it.

### Must-have functional requirements

- **FR-01:** Risk transitions shall validate allowed states and persist an audit record atomically with the state update.
- **FR-02:** Risk-list filters shall be applied server-side to project, package, and message text, plus workflow state.
- **FR-03:** Requirements parsing shall accept package names, version constraints, and Python-version markers; unsupported editable and URL lines shall be counted for review.
- **FR-04:** Decision submission shall require at least two distinct normalized package names.
- **FR-05:** Form routes shall use POST-Redirect-GET for successful risk updates.

### Non-functional, accessibility, and performance requirements

- **NFR-01:** Existing workspace APIs and product-domain behavior must remain backward compatible.
- **A11Y-01:** Risk tables shall include a caption, keyboard-accessible overflow, labels for row actions, visible focus, and non-color status text.
- **A11Y-02:** Validation errors shall be exposed through `role="alert"`, and form values shall remain available after error.
- **PERF-01:** Risk filtering shall be performed in one parameterized SQLite query rather than in-memory post-processing.
- **REL-01:** Invalid and missing risk transitions shall not corrupt state and shall return the user to a recoverable screen.
- **SEC-01:** Search values and form values shall be parameterized or escaped before use.
- **PRIV-01:** Telemetry shall record event type and state metadata only, not dependency files, free-text risk messages, or uploaded content.
- **TEST-01:** Every v0.7 behavior shall have unit/component or integration acceptance coverage, and existing product tests shall remain green.

### Architecture decisions

The changes remain server-rendered and standard-library-first to match the existing architecture. Risk history and telemetry share the same UI SQLite database and transaction as state changes. This is appropriate for the current single-process product UI. A production multi-instance deployment should later consolidate these tables into the main transactional database.

Requirements text parsing is deliberately conservative. It extracts package identity and Python markers needed by the current planner and flags complex source lines instead of pretending they were analyzed.

## 5. Testing

### TDD notes

The v0.7 acceptance test file was added first. All six tests failed against v0.6 behavior. Production code was then implemented and refactored until the new acceptance tests and the existing product suites passed.

### Added coverage

- Risk search/state filtering and accessible row actions.
- State transition history and telemetry.
- Requirements-style input and unsupported-line feedback.
- Truthful empty-workspace freshness.
- Accessible decision validation and value preservation.
- Route-level POST-Redirect-GET behavior with filter preservation.

### Validated suites

- `tests/test_product_ui_v07.py`
- `tests/test_product_ui.py`
- `tests/test_product_capabilities.py`
- Focused regression suite covering the modified UI, routes, and existing product capabilities: **25 passed**.
- Ruff linting for all files changed in v0.7.
- Editable package installation using `uv pip install -e ".[dev]"`.
- ZIP integrity using `unzip -t`.

### Remaining gaps

Browser-driven end-to-end and automated axe scans are not present in the repository. The complete legacy suite was started but exceeds the available validation window because it contains long-running/external-dependent cases; the focused product regression is green. A concurrent full-suite attempt is not authoritative because legacy tests share a SQLite database. Repository-wide Ruff also reports pre-existing findings in untouched legacy files, while all v0.7 changed Python files pass. Authentication and multi-tenant security tests are deferred until those capabilities are implemented.

## 6. Setup and migration notes

Install and run:

```bash
uv venv
uv pip install -e ".[dev]"
uv run uvicorn python_depot.api:app --reload
```

Run the focused v0.7 tests:

```bash
uv run pytest -q tests/test_product_ui_v07.py tests/test_product_ui.py tests/test_product_capabilities.py
```

Existing product UI databases are forward-compatible. New `risk_history` and `telemetry_events` tables are created automatically when `ProductUiService` starts. No destructive migration is performed.
